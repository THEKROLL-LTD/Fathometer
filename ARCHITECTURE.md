# Fathometer — Architecture

Fathometer collects Trivy filesystem scans from root servers and presents them for triage in a calm dashboard.

This document describes the **current state** of the architecture. The rationale for individual decisions lives as ADRs under [`docs/decisions/`](docs/decisions/); relevant ADRs are referenced inline where useful.

## 1. Vision

The focus is narrow: quickly see whether critical vulnerabilities are open on your own servers and need patching, with a gapless history for audits and an LLM-assisted assessment that pre-digests CVE details. The model for UX and self-hosting spirit is [uptime-kuma](https://github.com/louislam/uptime-kuma): minimal-friction setup, one container compose, an unfussy UI, lean dependencies. At its core Fathometer needs only the database; the only external integration is an **OpenAI-compatible LLM provider** for risk assessment and chat (freely chosen, locally runnable, fully disableable — air-gap-capable). The optional agentic upstream search (default off) is the only component with general web egress.

Fathometer cares about what is installed **on the running server** — OS packages (apt/dnf/apk) as well as statically installed binaries (k3s, tailscale, in-house tools). Trivy's filesystem scan covers both classes. Container-image scans, Kubernetes operator workflows, and code-repo scans belong in other tools and are explicitly not this app's job.

**Target audience:** operators with a handful to a few dozen root servers — small companies, hosting customers, clubs, well-tended hobby infrastructure. Fathometer fills the gap between "a cron plugin that emails update notices" (no overview, no prioritization, no history) and "a full SIEM/vuln-management suite" (too complex, too expensive). Fathometer is operable by someone outside the cybersec/DevOps field who checks in once or twice a week.

### Security stance: push, not pull

One central decision shapes everything else: **the app has no access to the servers it monitors.** Servers actively push their Trivy scans (via cron or a systemd timer); Fathometer never initiates a connection to the fleet. There are no SSH keys, no server passwords, no sudo credentials, and no inbound connections to the monitored hosts anywhere in the system.

The background is a real attack class: a central management tool collects credentials for many servers in one place and thereby becomes a worthwhile target — whoever compromises it gets the whole fleet. With Fathometer, an attacker who compromises the server sees only the vulnerability list — no direct access to the servers. The only secret value is the **master key**, with which servers register and negotiate their own server key. A leak only allows registering phantom servers (immediately visible in the audit log) and does not harm the real servers.

## 2. Scope

**In scope:** server registration via master key; receiving Trivy JSON scans (vuln scanner only); dedup of findings across re-scans; status workflow (`open` → `acknowledged`, automatically `resolved` when gone); global severity threshold; **EPSS and CISA-KEV signals** plus the numeric CVSS-v3 score as the central triage levers; "fix available" filter; bulk-acknowledge across servers; group-by-package view; stale-server and stale-Trivy-DB detection; server tags with filtering; global CVE search; URL-persistent filters for shareable views; multiple notes per finding (discussion thread); server-retirement workflow; CSV export of filtered findings; asynchronous LLM risk reviewer per application group; **focused LLM chat per `(server, application group)`** (Block AE, ADR-0055) — operator assistance via a "Help" button per group row, snapshot context, SSE streaming; **optional, operator-gated agentic upstream-update search** (Block AI, ADR-0063 — default **off**, dedicated `research-worker`, advisory: shows, with citations, whether a fixed build already exists upstream, **never** an auto band flip); a complete audit log; single-user auth and a first-boot wizard.

**Out of scope:**

- Notifications of any kind (mail, webhooks, push).
- Multi-user / RBAC / SSO.
- Mobile-responsive layout (desktop-first).
- **Unfocused, server-wide LLM chat** — the old "Request AI assessment" over *all* findings of a server was removed without replacement in ADR-0050 and is not coming back. In its place (in scope, see above): the **focused chat per `(server, application group)`** (ADR-0055) and the **optional agentic upstream-update search** per researchable finding (ADR-0063). The difference is focus: per application group or per finding with frozen context, not an open server-wide chat.
- Container-image and code-repo scans.
- Secret/misconfig findings in the UI (schema prepared via `finding_type`, activatable later without a migration).
- Trend graphs over long time ranges; PDF export.
- Distributed rate-limit backend (Redis) / multi-instance deploy.
- SBOM and license findings.

## 3. Tech stack

**Backend:** Python 3.14 (EL10 AppStream stream; `requires-python >= 3.13`), Flask, SQLAlchemy 2.x + Alembic, Pydantic v2. Persistence on PostgreSQL 17 in its own container. `structlog` (logging with a redaction filter), `flask-limiter` (rate limits), `nh3` (HTML/Markdown sanitization), `argon2-cffi` (password/master-key hashing), `cryptography` Fernet (LLM API-key encryption).

**Frontend:** Jinja2 server-side rendered, HTMX for partial DOM updates and SSE, Alpine.js for client-side UI state (modals, dropdowns, filters). Styling is **100% hand-written plain CSS** based on a custom design-token set (`frontend/src/css/tokens.css`) plus BEM-style component stylesheets — no Tailwind, no DaisyUI (ADR-0032). The build runs through **esbuild** (JS: Alpine + HTMX vendored as `vendor.js`, app modules as `app.js`) and **lightningcss** (CSS minify, autoprefix, hash naming) in a build-only Docker stage (`node:20-alpine`). The production image (base `AlmaLinux 10-minimal`, builder on `almalinux:10`) contains no Node runtime, only the finished static files under `app/static/dist/`. The interpreter is EL10's packaged AppStream `python3.14` stream (EL10 ships no python3.13; `requires-python >= 3.13` is satisfied by 3.14 — no source build needed), and AlmaLinux's OVAL/ALSA errata give Trivy authoritative, backport-aware fix-state — far less OS-package noise than the Debian tracker (ADR-0069, replaces Debian `python:3.13-slim-trixie`). A `manifest.json` maps logical names to hashed files; a Jinja context processor provides the `{{ asset_url(...) }}` helper. All assets (fonts, JS, CSS) are self-hosted — no external CDN resources (air-gap-capable).

**LLM:** the client speaks exclusively the OpenAI-compatible chat-completions protocol via the official `openai` Python SDK with configurable `base_url`/`api_key`/`model`. The default provider preset is **DeepInfra** (`https://api.deepinfra.com/v1/openai`); one provider, but **separate default models per consumer** (ADR-0057, supersedes the V3 default from ADR-0010): `openai/gpt-oss-120b` for the risk reviewer, `deepseek-ai/DeepSeek-V4-Flash` for the per-group chat and (optionally) the upstream search. Only OpenAI-standard features are used, so switching to OpenAI, Together, Groq, local Ollama/vLLM, or a LiteLLM proxy is a pure setting change. The agentic upstream search additionally uses `pydantic-ai` for a typed agent loop (separate path, §11).

**Deployment:** docker-compose with **one** app image build that runs in several containers with different entrypoints (web `fathometer-app`, `fathometer-llm-worker`, optional `fathometer-research-worker`) plus a dedicated Postgres container — topology and responsibilities see §4. Workers have no inbound port; the research-worker is default off and omitted in air-gap setups. UI and doc language: English everywhere (see `CLAUDE.md`).

```
   └─────────────────┬───────────────────┘    │   default)   │
                     │ psycopg                 └──────▲───────┘
                     ▼                                │ LLM egress
   ┌─────────────────────────────────────┐           │ (research-worker
   │      Postgres container             │           │  also web egress)
   └────────┬────────────────────┬───────┘           │
            │ psycopg            │ psycopg           │
   ┌────────┴─────────┐  ┌───────┴────────────────┐  │
   │ fathometer-      │  │ fathometer-research-   │──┘
   │ llm-worker       │  │ worker (opt-in, off)   │
   │ ingest + pass1/2 │  │ upstream-update search │
   └──────────────────┘  └────────────────────────┘
                     ▲
                     │ HTTP POST /api/scans (Bearer: server key)
   ┌─────────────────┴───────────────────┐
   │   N × root server with Trivy + cron │
   └─────────────────────────────────────┘
```

**Containers (all from the same image build, different entrypoints, via docker-compose):**

- **`fathometer-app`** (web) — stateless, the only container with an inbound port. Serves the UI (HTMX fragments), the server-facing API (`/api/scans` etc.), and the SSE per-group-chat stream. Sessions in signed cookies (Flask-Login with `SECRET_KEY` from the settings). LLM egress only for the interactive chat.
- **`fathometer-llm-worker`** — no inbound port. Processes the asynchronous scan-ingest queue (`scan_ingest_jobs`) **and** the two-pass risk reviewer (pass 1 group detection, pass 2 risk evaluation per fix lane) over the `llm_jobs` queue with `FOR UPDATE SKIP LOCKED`, a stale reaper, and periodic re-enqueue sweeps (§11). DB connect + LLM egress.
- **`fathometer-research-worker`** — no inbound port, **opt-in (default off, ADR-0063)**, omitted in air-gap deployments. Dedicated path for the agentic upstream-update search; polls **only** `upstream_check_results` (does not touch `llm_jobs`), runtime is a typed `pydantic-ai` agent loop. The only container with general **web egress** (its own outbound allowlist) in addition to LLM egress.
- **`postgres`** — its own container (not all-in-one). Single source of truth; all persistent data and all job queues live here — the worker fan-out needs **no** additional message-broker backend.

All workers are horizontally **not** scaled (single instance, in-process concurrency — ADR-0029); multi-instance/distributed locking is out of scope. Worker liveness via a heartbeat column in the DB, no HTTP healthcheck port.

## 5. Data model

Few tables, clear relationships. Raw Trivy JSON is **not** persisted — after Pydantic parse and findings extraction the body is discarded (scans are large, the forensic value is low because `findings` plus the audit log retain everything relevant).

- **`users`** — exactly one admin user (username, Argon2 hash). More users later without a schema break.
- **`servers`** — registered host: name, hashed API key, expected scan interval (for stale detection), last-scan timestamp, nullable `revoked_at` (instead of deletion, for audit) and `retired_at`. Plus denormalized host info from the last scan (`os_family`, `os_version`, `os_pretty_name`, `kernel_version`, `architecture`, `agent_version`, `trivy_version`, `agent_version_seen_at`, `host_state_snapshot_at`), Trivy-DB freshness (`trivy_db_version`, `trivy_db_updated_at`), and an optional 1:N host-group assignment `group_id` (ADR-0034).
- **`server_groups`** — host groups (ADR-0034, Block W): named 1:N buckets for sidebar/dashboard structure (`name`, ordering). A server belongs to **at most one** group (`servers.group_id`, `ON DELETE SET NULL`); no forced default group. Orthogonal to `tags` (m:n filter) — groups are the structural hierarchy, tags the free cross-cutting markup.
- **`scans`** — pure receipt bookkeeping per ingested scan (server, `received_at`, versions, historized host fields). No raw JSON.
- **`server_listeners` / `server_processes` / `server_kernel_modules` / `server_services`** — the host snapshot (Block O, ADR-0022; populated from `host_state`, §6). Four tables, one per snapshot block, **truncate+insert per server** (no merge — always the current state). They feed the risk reviewer's exposure reasoning (PUBLIC-EXPOSED/LOOPBACK-ONLY) and are defensively volume-capped.
- **`daily_risk_state`** — per `(server, day)` the aggregated risk state for the uptime-kuma-style heartbeat bar (ADR-0035). Pure display mapping, derived live from the findings and persisted per day; not a triage input.
- **`tags` / `server_tags`** — free tag names (`prod`, `web`, `region-eu`) as an m:n bridge. In the dashboard they are filter chips, AND-combined.
- **`findings`** — the operational core table. Unique per `(server_id, finding_type, identifier_key, package_name)`. `finding_type` enum (`vulnerability`/`secret`/`misconfig`; in the MVP only `vulnerability`), `identifier_key` is the natural ID per type (vuln: CVE ID). `finding_class` enum (`os-pkgs`/`lang-pkgs`/`other`) from the Trivy `Class` field enables a "OS packages only" vs. library-findings filter. Shared fields: installed/fixed version, severity enum, title/description, `first_seen_at`, `last_seen_at`, `status` (`open`/`acknowledged`/`resolved`) with `acknowledged_at/by` and `resolved_at`. Vuln fields: `cvss_v3_score`, `cvss_v3_vector`, `epss_score`, `epss_percentile`, `is_kev`, `kev_added_at`, `cwe_ids`, `attack_vector`, `references`. `has_fix` is a generated column (`fixed_version IS NOT NULL AND != ''`). Cause fields (`package_purl`, `target_path`, `result_type`, `severity_source`, `vendor_ids`) distinguish distro package vs. embedded library. Host-update fields (`host_update_available`, `owning_package`, `available_version`; ADR-0062) hold whether the owning OS package is repo-updatable. Risk fields: `risk_band` (nullable until the first pre-triage), `risk_band_source` (`engine`/`llm`/`manual`), `risk_band_computed_at`, `severity_by_provider` (JSONB, Trivy `VendorSeverity` map as pre-triage input), `vendor_status` (normalized), `application_group_id`, `primary_url`. **There is no per-finding `risk_band_reason`** — the reason is group/lane-level and lives on the eval junction (ADR-0054). An acknowledge/reopen comment is **always optional** — when present it becomes the first note in the thread, otherwise the audit event alone records the action.
- **`finding_notes`** — discussion thread per finding (`author`, `text`, `created_at`, `deleted_at` for soft-delete; notes are never hard-deleted).
- **`application_groups` / `application_group_evaluations`** — application-group grouping. The group holds fleet-wide identity + match patterns (`label`, `path_prefixes`, `pkg_name_*`, `pkg_purl_pattern`, `group_kind`, `source`). The server-dependent evaluation (`risk_band`, `reason`, `worst_finding_id`, `action_type` …) lives in the junction. Since ADR-0053 (fix-lane evaluation) the PK is **three-column** `(group_id, server_id, fix_lane)` with `fix_lane ∈ {patch, mitigate}` — up to **two** eval rows per `(group, server)`, one per fix lane. `fix_lane` is derived deterministically from `Finding.fixed_version`, `Finding.finding_class`, and `Finding.host_update_available` (single source `risk_engine.fix_lane_for` + mirroring SQL `case`): `patch` = host-applicable fix (`os-pkgs` with `fixed_version`, **or** lang-pkgs with `host_update_available=true` — ADR-0062, the owning OS package is updatable), `mitigate` = not host-applicable (no fix, **or** a lang-pkgs/`other` fix that only an upstream rebuild closes). **ADR-0061 history:** AG temporarily introduced a third `upstream` lane for lang-pkgs fixes; **ADR-0064 (Block AK) took it back** — it collapses into `mitigate`, and the "fix exists upstream" info is now finding-level (`fixed_version` + an upstream-check button per row), because the operator action is identical and a separate band offered no foresight. AG's correctness core remains: a lang-pkgs fix never lands in `patch`/`act` (no false "Apply app update"). The lane itself is neither a persisted finding column nor an LLM output (`host_update_available`/`owning_package`/`available_version`, by contrast, are persisted, nullable finding columns). This way multiple servers evaluate the same group pattern without a last-write-wins conflict, and the host-patchable vs. non-host-patchable part of a group can carry different bands. Findings inherit their band from the junction row responsible for their server **and their lane**.
- **`audit_events`** — every state-changing action with `ts`, `actor` (username/server name/`system`), `action` (enum, §11), `target_type/id`, optional `comment`, and a `metadata` jsonb.
- **`settings`** — single row (`CHECK id = 1`): severity threshold, hashed master key, stale threshold (`stale_threshold_h`), stale-DB threshold (`stale_trivy_db_threshold_h`), `setup_completed_at` flag. **LLM provider block** (`llm_provider_name`, `llm_base_url`, `llm_api_key_encrypted`, `llm_reviewer_model`, `llm_chat_model`, `llm_daily_token_cap`). **Reviewer runtime** (the worker reads the same row, §11): `block_p_llm_mode` (`off`/`observation`/`live`), `llm_worker_heartbeat_at` + `research_worker_heartbeat_at` (worker liveness), token-budget counters (`llm_token_budget_used_today`/`_reset_at`), `llm_worker_job_concurrency`, `llm_debug_log_success_sample_rate`. **Upstream-check block** (ADR-0063, **default off**): `upstream_check_enabled`, `upstream_search_backend` (searxng/tavily/firecrawl/serper), `upstream_search_base_url`, Fernet-encrypted `upstream_search_api_key_encrypted` + optional SearXNG basic auth (`upstream_search_username`/`_password_encrypted`), `llm_research_model`. **One shared provider, two models** (ADR-0057, Block AF, migration `0024`): `llm_reviewer_model` (nullable, default `openai/gpt-oss-120b`) feeds the risk reviewer (worker, pass 1 + 2); `llm_chat_model` (`NOT NULL` with `server_default` `deepseek-ai/DeepSeek-V4-Flash`) the per-group chat. `base_url`/`api_key` stay shared — no multi-provider. Theme is statically dark (no toggle).
- **`group_chat_conversations` / `group_chat_messages`** — per-group AI chat (Block AE, ADR-0055, migration `0023`). Exactly **one** conversation per `(server_id, application_group_id)` (`UNIQUE` constraint `uq_group_chat_conversations_server_group`); both FKs `ON DELETE CASCADE`. `server_id` is `Integer` (`servers.id`), `application_group_id` is **`BigInteger`** (`application_groups.id` is BigInteger — like `application_group_evaluations`/`llm_debug_log`). `model` holds `Setting.llm_chat_model` at snapshot time (ADR-0057, formerly `llm_model`); `findings_snapshot_at` only the freeze timestamp (debug/audit). There is **no findings bridge table** — the frozen findings snapshot lives in the persisted system prompt (first message, `role=system`). `group_chat_messages` carries `role` as the native enum `chat_message_role` (`system`/`user`/`assistant`), `content` (Text), optional `prompt_tokens`/`completion_tokens`, and a lookup index `(conversation_id, created_at, id)`. "New Chat" deletes the conversation (CASCADE on the messages); the next message creates it fresh.
- **`upstream_check_results`** — queue + request + result cache of the agentic upstream-update search (Block AI, ADR-0063, migration `0027`) in **one** table. Key `UNIQUE(artifact_module, installed_version)` (= one artifact@version = one in-flight job = one cache entry); `artifact_module` is the binary basename (not the component PURL). `status` (`queued`/`running`/`done`/`error`) + `attempts`/`picked_up_*`/`next_attempt_at` make the row the `research-worker`'s job queue; seed-snapshot columns (`cve`/`vulnerable_component`/`fixing_component_version`/`ecosystem`/`binary_path`/`search_hint`/`description`) keep the research request self-contained (no finding FK needed); the `Verdict` columns (`delivery`/`latest_release_component_version`/`fixed_build_release`/`operator_action`/`confidence`/`sources_used` JSONB/`reasoning`/`model`/`error`) + `checked_at` (TTL) the result. Advisory — no FK to findings, no auto band flip.
- **Queues, caches & feeds (infrastructure).** `scan_ingest_jobs` — asynchronous scan-ingest queue (ADR-0026, idempotency via `payload_sha256`, gzip payload until `done`/retention). `llm_jobs` — reviewer job queue (pass 1/2, `depends_on`, `FOR UPDATE SKIP LOCKED`, stale reaper). `llm_risk_cache` — pass-2 verdict cache (`cache_key` incl. `fix_lane` salt + lane-OPEN-set fingerprint, TTL 30 days, LRU; §11). `llm_debug_log` — sampled LLM-call diagnostics (success via `llm_debug_log_success_sample_rate`, errors 1:1). `epss_scores` / `cisa_kev_catalog` — mirrored EPSS/KEV feeds (ADR-0024), `feed_pull_log` their pull health (close to §14). All job queues live in Postgres — no separate message broker.

**Indexes** (in addition to PKs/FKs): `findings(server_id, status)`, `findings(identifier_key)`, `findings(is_kev) WHERE is_kev`, `findings(epss_score DESC) WHERE status='open'`, `findings(package_name, server_id) WHERE status='open'`, `findings(risk_band) WHERE status='open'`, `findings(application_group_id)`, the consolidated covering index `ix_findings_server_open_triage` (server-detail aggregates as an index-only scan), `audit_events(ts DESC)`, plus the junction indexes.

**Dedup & resolve:** at ingest, each finding runs an upsert on `(server_id, finding_type, identifier_key, package_name)` — if it exists, the volatile fields (versions, severity, CVSS, EPSS, KEV, …) are updated and the status stays; otherwise it is created `open` with `first_seen_at=now()`. In a second phase, all `open`/`acknowledged` findings of that server that are no longer in the current scan set are set to `resolved`. That is (besides server retirement) the only auto-resolve site.

## 6. API

Two aspects: server-facing (Trivy push clients, Bearer/master-key auth) and browser-facing (UI, mostly HTMX HTML fragments, session auth).

### Server-facing

- **`POST /api/register`** — body `{master_key, name, expected_scan_interval_h?}`. Validates the master key, creates a server, generates a 256-bit server key, and returns `{server_id, api_key}`. Only the hash is stored.
- **`POST /api/scans`** — `Authorization: Bearer <server_key>`. The body is a **wrapper envelope** (not the bare Trivy JSON):

```json
{
  "agent_version": "0.3.0",
  "host": { "os_family": "ubuntu", "os_version": "22.04", "os_pretty_name": "...",
            "kernel_version": "...", "architecture": "x86_64", "trivy_version": "0.70.0" },
  "host_state": { "snapshot_at": "...", "tools_available": [...], "gaps": [],
                  "listeners": [...], "processes": [...],
                  "kernel_modules": [...], "services": [...] },
  "host_updates": [ { "path": "usr/sbin/tailscaled", "owning_package": "tailscale",
                      "available_version": "1.98.5-1", "update_available": true },
                    { "pkg_name": "kernel", "owning_package": "kernel",
                      "available_version": null, "update_available": false } ],
  "scan": { /* trivy rootfs --format json, from agent v0.2.0 without Results[].Packages[] */ }
}
```

  `host` and `agent_version` are required; `host.trivy_version` (from agent 0.2.0), `host_state` (from agent 0.3.0), and `host_updates` (from agent 0.7.0, ADR-0062; os-pkgs entries from agent 0.8.0, ADR-0066) are optional and forward-compatible, typed as `… | None`. `host_updates` carries two entry shapes with one join key each (exactly one set per entry): **lang-pkgs** via `path` (= Trivy `Result.Target`, joined against `Finding.target_path`) and — since ADR-0066 — **os-pkgs** via `pkg_name` (= Trivy `PkgName`, joined against `Finding.package_name`; os-pkgs have no binary `Target`, hence **no** `rpm -qf` — the owning package **is** the `PkgName`). Per entry the host agent reports, read-only, the owning OS package and whether its repo has an update; the ingest persists this per finding (`host_update_available`/`owning_package`/`available_version`). The fix-lane derivation promotes a **lang-pkgs** finding with `host_update_available=true` to `patch`; for **os-pkgs** the flag is pure pass-2 reviewer enrichment (the lane stays invariant `patch`, ADR-0066). If the block is missing (old agent / not resolved) → `NULL` → for lang-pkgs conservatively `mitigate` (ADR-0064 — the "fix exists upstream" info is shown finding-level), for os-pkgs the reviewer falls back to a pure version comparison (`fixed` vs. running kernel). Trivy-DB freshness is extracted by the server itself from `scan.Metadata`. The `host_state` block is defensively bounded (max 4096 `listeners`/`processes`, 1024 `kernel_modules`/`services`, 32 `tools_available`/`gaps`); if its validation fails, only it is dropped (audit `host_state.parse_failed`), the findings ingest proceeds, and pre-triage marks the findings `risk_band=unknown`.

  The endpoint accepts `Content-Encoding: gzip` (typically 8–10× compression) and decompresses streaming with a hard decompress bound (§8) before the Pydantic parse. **Processing is asynchronous:** the edge handler responds within <1 s with `202 Accepted` and `{job_id, status:"queued"}`; the full processing (parse, findings upsert, host-state persist, pre-triage, group matching, LLM-job queueing) runs in the worker. Idempotency via a partial-unique index on the `payload_sha256` of the queued/in_progress jobs. The agent is fire-and-forget (no polling, no status endpoint); progress is visible server-side via the job row and the dashboard. The gzipped payload is atomically nulled on the status change to `done`; on `failed` it stays 24 h for debugging, then a retention DELETE.
- **`POST /api/keys/rotate`** — master-only, body `{master_key, target:'master'|'server', server_id?}`. Rotates the key and returns the new plaintext once.

These are all server-facing endpoints (Bearer/master key). Server **lifecycle** (revoke/retire/delete-findings/delete) is **browser-facing** under `/settings/servers/<id>/...` (session auth, POST) — there is **no** `DELETE /api/servers/{id}`. In addition there are public, auth-free agent-bootstrap routes (`GET /install.sh`, `/agent/files/<name>`, `/agent/version`, plus `/uninstall.sh`; §10) and two health endpoints (`GET /healthz`, `GET /readyz`).

### Browser-facing (HTMX)

Endpoints return HTML fragments (paired with Jinja partials in `templates/_partials/`).

- **Findings:** `POST /findings/<id>/acknowledge`, `/reopen` (both optional `comment`); `POST /findings/<id>/notes`, `POST /findings/<id>/notes/<note_id>/delete` (soft-delete — POST, no `DELETE` verb); `POST /findings/group/acknowledge` (group-row ack); `GET /findings` (bucket view by `(server, application group)`, ADR-0037), `GET /findings/bucket`, `GET /findings/pending`; `GET /findings/export.csv?<filter>` (cross-server mode without a row limit).
- **Bulk-acknowledge** — two endpoints: (1) `POST /api/findings/bulk-acknowledge` (JSON in/out) in three flavors, exactly one filled: **A** explicit `finding_ids`; **B** `match` (CVE ID/package name, optional tag/status) across the whole fleet; **C** `server_scope` (`{server_id, risk_band}`) — the server itself resolves all open findings of that band (no ID transport, no limit; `risk_band` whitelist `escalate/act/mitigate/monitor/noise`, `pending`/`unknown` → 422). `dry_run:true` returns a preview for the modal. (2) `POST /findings/bulk/acknowledge` (HTML response) for the `/findings` bucket view: `bucket_selections` + explicit IDs are resolved to IDs server-side (ADR-0037). Both audit with a capped ID list + full `count` in `metadata`.
- **Tags & groups (hybrid lifecycle, ADR-0040):** inline create + assignment at the server-settings sub-view under `/servers/<id>/settings/...` (`POST tags/add`, `tags/<tag_id>/remove`, `tags/create`, `group`, `group/create`, `scan-interval`); pure management (rename/color/delete/move, POST — no `DELETE` verb) under `/settings/tags/...` and `/settings/groups/...`, plus the lists `GET /settings/tags` / `/settings/groups`.
- **Server lifecycle:** under `/settings/servers/<id>/...` — `POST .../revoke`, `.../retire` (marks open findings `resolved`, reason "server retired"), `.../delete-findings` (deletes **all** findings of the server, any status, irreversibly — the server row and audit trail stay, `finding_notes` fall via FK CASCADE; only a single `server.findings_deleted` event with `deleted_count`), `.../delete`.
- **Per-group chat & upstream check (JSON/SSE, session auth):** under `/servers/<sid>/groups/<gid>/chat` (`GET` sub-view, `POST /messages`, `GET /stream` = SSE, `POST /new`; Block AE) and `/servers/<sid>/groups/<gid>/upstream-check` (`POST` enqueue, `GET` poll; Block AI, one `(server,group)` guard against IDOR).
- **Dashboard/filter:** `GET /` and `GET /servers/<id>` with all filters URL-encoded → bookmarks and share links work without separate persistence; live partials (`/_partials/dashboard/kpis`, `/_partials/sidebar`, server-detail `/fragments/...`) serve the polling fragments.

**Live updates** run over **HTMX polling**, not SSE: the dashboard pane and the sidebar server list poll their own partial route every 10 s, throttled to visible tabs (`document.visibilityState`). The only **SSE endpoint** is the per-group-chat token stream `GET /servers/<id>/groups/<gid>/chat/stream` (Block AE, ADR-0055). The former server-wide LLM-chat stream `GET /chat/{conversation_id}/stream` was removed in ADR-0050 and does **not** return; the new stream is focused per application group (§11).

## 8. Auth and DoS protection

**Auth.** UI auth is single-user, session-based, Argon2id password, Flask-Login with a 7-day timeout. Server auth is two-layered: the **master key** (256-bit, Argon2id hash in `settings`) only for `register` and `keys/rotate`; **server keys** (256-bit per server, SHA-256 hash suffices due to high entropy) for scans, plaintext issued only once. The LLM-provider API key is Fernet-encrypted (key from ENV `FM_ENCRYPTION_KEY` — if missing, the app refuses to start). CSRF protection on all state-changing browser endpoints (Flask-WTF, HTMX sends the token in the header).

**DoS.** The unauthenticated endpoints are the main attack surface. The order in `/api/scans` is strict: **body-size limit** (`MAX_CONTENT_LENGTH`, default 64 MB wire, configurable via `FM_MAX_BODY_MB`) → **auth check** (Bearer against `api_key_hash` with `hmac.compare_digest`, on mismatch an immediate 401) → **gzip decompress** with a bound (`FM_MAX_DECOMPRESSED_MB`) against zip bombs → parse. This way an anonymous attacker cannot push large JSON structures through the parser. **Rate limiting** (`flask-limiter`, per IP and per server key, all overridable via ENV): `register` 10/min, `login` 5/min, `scans` unauth 20/min, scans auth 60/h. **Per-server soft cap** on open ingest jobs (`FM_MAX_QUEUED_INGEST_JOBS`, default 50 → 429) so a server cannot flood the worker queue. **Sanity checks** after parse: max 50,000 vulns/scan, max 64 KB/string field → 422. **Login brute-force** is naturally capped by Argon2id (100 ms+) plus the rate limit; failed logins land in the audit log. **LLM cost protection:** the LLM consumer capped by the daily token cap (`llm_daily_token_cap`, operator-controllable via the provider tab, initial seed `FM_LLM_TOKEN_BUDGET_DAILY` default 2 M, reset 00:00 UTC) is the risk-reviewer worker (§11); the cap pauses it on exhaustion. The interactive per-group chat (Block AE, §11) deliberately does **not** call `llm_budget` — low-frequency, manually triggered operator use, throttled solely via `flask-limiter` (stream 60/h, messages 30/min per conversation).

**Production recommendation (README):** the app alone is not hardened against layer 4 — a reverse proxy (nginx/Caddy/Traefik) belongs in front of it for TLS, connection limits, slow-loris protection, and ideally an IP allowlist on `/api/scans`.

## 9. Input validation and sanitization

Every Trivy JSON is treated as hostile input — a valid server key only says "authorized", not "safe". Defense in depth: Pydantic + regex + ORM + Jinja autoescape are redundant against injection.

- **Strict Pydantic schema:** `Severity` is `Literal[...]`, length limits per field, unknown top-level fields are ignored (forward-compat), unknown fields in validated structures stripped. Validation errors → 422 with field names.
- **Regex whitelists per field type:** vuln IDs **CVE or GHSA** (`^CVE-\d{4}-\d{4,7}$` resp. `^GHSA-[a-z0-9]{4}-[a-z0-9]{4}-[a-z0-9]{4}$`), package names `^[a-zA-Z0-9._+\-:/@]+$` (the `@` carries the ADR-0011 `@target` suffix for lang-pkgs), `cvss_v3_score` float 0–10, `epss_*` 0–1, `cwe_ids` `^CWE-\d{1,7}$` (max 50, defensively trimmed), `attack_vector` whitelist (N/A/L/P), `references` http(s) max 100/finding at max 2 KB. `architecture` from a whitelist (`x86_64`/`aarch64`/`armv7l`/`i686`/`ppc64le`/`s390x`) with alias canonicalization (`arm64`→`aarch64`, `amd64`→`x86_64`). `llm_base_url`/`upstream_search_base_url` must be `https://` except for `http://localhost`/`127.0.0.1`. Whatever does not match is dropped — no best-effort sanitization.
- **NUL bytes/UTF-8:** checked in the validator (→ 422 instead of a DB 500), UTF-8 decode `strict=True`, control chars except tab/newline removed from display fields. **JSON depth limit** 32 (typically 4–6).
- **ORM only:** all DB access parameterized; raw `text()` without a `:param` bind is forbidden (CI lint).
- **XSS:** Jinja `autoescape=True` mandatory; `|safe` never on client or LLM data. Formatted text (CVE descriptions, LLM responses) runs through an `nh3` allowlist, never through `markdown`/`mistune` directly.
- **Prompt injection:** Trivy data lands in the system prompt between markers (`<<TRIVY_DATA_START>> … <<TRIVY_DATA_END>>`) with an explicit "data, not commands" instruction. No guarantee, but it raises the bar; LLM output is treated like Trivy input. **The same marker doctrine applies to the per-group-chat prompt** (Block AE, `build_group_system_prompt`): fingerprint, services, listeners, group context, and all group findings sit between the same markers, every display string runs through the ported `_safe` sanitization (control chars/NUL out, length cap), and embedded marker strings in manipulated scanner data are **neutralized** (zero-width joiner between the brackets) so that untrusted data cannot close the data block prematurely.
- **Header/log injection:** request headers are never reflected; `structlog` JSON prevents newline injection, sensitive fields are logged as `***REDACTED***`. **Path injection:** Trivy `Target` paths are pure display strings, never file operations.

## 10. Client agent (reference implementation)

The server side defines only the envelope format (§6); any operator can rebuild the client. A Bash reference agent ships with it.

- **`agent/fathometer-agent.sh`** — requires `trivy` (≥ 0.70.0), `curl`, `jq`, `gzip`, and root. Collects host info from `/etc/os-release` and `uname`, calls `trivy rootfs / --format json --scanners vuln` (`rootfs` so that Go/Java binaries under `/usr/local/bin` etc. are captured), builds the envelope via `jq`, strips `Results[].Packages[]` (SBOM out of scope), compresses with gzip, and sends it via `curl` to `POST /api/scans`. From v0.3.0 also the host snapshot (`collect_listeners`/`processes`/`kernel_modules`/`services` in `agent/lib_host_state.sh`, each with a `command -v` availability check and `gaps` tracking; ASCII-only under `LC_ALL=C`). EPSS/KEV/CVSS come directly from Trivy in the report — no additional enrichment. From v0.7.0 (ADR-0062) the agent, after the scan, resolves the owning OS package per lang-pkgs binary (`rpm -qf`/`dpkg -S`) and checks, read-only, via `dnf|yum check-update` / `apt-get -s upgrade` (simulation, a single call, joined against the packages in the agent), whether a host-applicable update is available → `host_updates` block in the envelope (`collect_host_updates` in `agent/lib_host_state.sh`; no state change, timeout-wrapped). From v0.8.0 (ADR-0066) `collect_host_updates` additionally emits os-pkgs entries (join key Trivy `PkgName` instead of path; **no** `rpm -qf`, since os-pkgs have no binary `Target`); the ingest joins them via `package_name` and the pass-2 reviewer uses them for stale-artifact FP correction (§12). From v0.6.0 (TICKET-015), after the agent self-update and before the scan, the run brings a **fathometer-managed** Trivy binary (`/opt/fathometer/bin/trivy`) up to `recommended_trivy_version` (`auto_update_trivy`: GitHub download with mandatory SHA256, atomic replace + `.bak` rollback, fail-soft; never a system Trivy; opt-out `FM_TRIVY_AUTO_UPDATE=0` for air-gap). From v0.10.0 (ADR-0067, TICKET-019) the `rootfs` call carries `--skip-dirs` keyed on containerd-internal-marker globs (`**/io.containerd.runtime.*.task`, `**/io.containerd.snapshotter.*`) covering all containerd distros (k3s/RKE2/k0s/MicroK8s/standalone/CRI) including the live `/run` task roots, plus explicit docker/podman/CRI-O roots (`/var/lib/docker`, `/var/lib/containers`, `/run/containers`, with the original containerd per-path roots kept as fallbacks) — their contents are unpacked container-image layers and container-image scanning is out of scope (§17); host OS package DBs and host binaries live outside these roots and stay covered. Operators append relocated data-roots via `FM_SCAN_SKIP_DIRS` (comma-separated absolute paths). The call also passes an explicit `--timeout` from `FM_SCAN_TIMEOUT` (default `5m`, Trivy's own default made explicit and operator-tunable). Exit codes 0/1/2/3 (OK / missing prerequisites / Trivy error / upload error).
- **`agent/fathometer-register.sh`** — registers a server with the master key (from `FM_MASTER_KEY` or a silent prompt) and prints the server key to stdout.
- **Bootstrap installer** — `curl -fsSL https://<host>/install.sh | sudo bash`. The backend renders an interactive Bash wizard script (system detection → dependencies → Trivy pin-install with SHA256 verify → server registration via TTY prompt → systemd unit+timer with `RandomizedDelaySec` → probe scan). The master key never via argv/ENV, only at the prompt. Non-interactive via `FM_UNATTENDED=1`. Four public routes (no auth, in `PUBLIC_PATHS`): `GET /install.sh`, `GET /agent/files/<name>` (whitelist), `GET /agent/version` (minimum/recommended versions from code constants), and `GET /uninstall.sh` (alias to the `fathometer-uninstall.sh` uninstaller, ADR-0049 — byte-identical to `/agent/files/fathometer-uninstall.sh`).
- **Controlled auto-updates:** before the scan the agent updates **itself** (`auto_update_self` — on a newer server version it downloads the agent script from `/agent/files/...`, with shebang/version-declaration guards, fail-soft, keeping the running version on error) and keeps the **fathometer-managed Trivy binary** at the recommended version (`auto_update_trivy`, mandatory SHA256, see above). Both are fail-soft: the self-update skips itself as soon as the server is unreachable (`FM_URL` missing / `/agent/version` times out) — air-gap-natural, no dedicated switch; the Trivy update is explicitly disableable via `FM_TRIVY_AUTO_UPDATE=0`.
- **What the agent does NOT do:** no file transfer other than the scan, no inbound listening, no writes outside `/tmp` and `/opt/fathometer/`, never touch a system Trivy. Push-only cron job/timer, no daemon.

## 11. LLM integration

Two LLM consumers: (1) the asynchronous **risk reviewer per application group** (worker, budgeted) and (2) the interactive **per-group AI chat** (Block AE, ADR-0055, group-scoped, **no token cap**). The former unfocused **per-server chat** — "request assessment" → conversation → SSE stream — was **removed without replacement in ADR-0050 (2026-06-07)** (including the three `llm_*` conversation tables) and does **not** return; ADR-0055 instead introduces a freshly designed, focused chat (its own `group_chat_*` schema, its own prompt).

**Per-group AI chat (interactive, Block AE).** The second LLM consumer alongside the reviewer, triggered via the "Help" button per group row (§7). The context is a **snapshot at chat start**: host fingerprint, active services, listeners (incl. exposure), and all OPEN findings of the group are rendered into the system prompt and persisted when the conversation is created (`findings_snapshot_at`); a re-scan does not change a running conversation — a deliberate deviation from the current-state doctrine (ADR-0052) in favor of internally consistent conversations, fresh context = "New Chat". Answers stream token-by-token via SSE over `LlmClient.stream_chat`; the assistant message is persisted after stream end in its own DB session. The chat **does not call `llm_budget`** and does not count against `llm_daily_token_cap` (ADR-0055 decision 4 — interactive operator use is low-frequency and manual, a cap would block in the triage moment; the cap from ADR-0014 still applies to the reviewer alone). **No function calling** (ADR-0002 still holds), model only from `Setting.llm_chat_model` (ADR-0057 — a separate chat model, distinct from the reviewer model). The prompt builder `build_group_system_prompt` (`app/services/group_chat_prompt.py`) applies the same marker doctrine as the reviewer (§9/§10 above). **Upstream verdict in the snapshot (Block AJ, ADR-0063 §Integration):** if a **completed** upstream-check verdict exists for the `(server, group)` (`upstream_check_results.status == 'done'`), it is included at chat start as an optional 8th block in the frozen system prompt — between the markers (untrusted, web/LLM-derived → `_safe` + marker neutralization), explicitly marked `candidate · verify` and with the note that it **never** changes the risk band. Same freeze semantics as the rest of the snapshot (a later re-check does not change a running conversation — "New Chat" pulls the fresh state); if no verdict exists, the block is absent.

**Agentic upstream-update search (optional, operator-gated, Block AI / ADR-0063).** A third LLM consumer, but deliberately a **separate path**: a dedicated `fathometer-research-worker` container (same image, `entrypoint python -m app.workers.research_worker`, no inbound port) instead of the reviewer worker. It answers on demand, per group row with a **researchable** finding (lang-pkgs with `fixed_version`, in the `mitigate` lane), the question "does a fixed release of this artifact already exist upstream?" (ADR-0064: since Block AK, "fix exists upstream" is finding-level rather than its own lane). **Default off** (`Setting.upstream_check_enabled`), its own model `Setting.llm_research_model` (shared provider), its own operator-configured search backend (SearXNG/Tavily/Firecrawl/Serper, key Fernet-encrypted). The runtime is a **typed `pydantic-ai` agent loop** with two of its own tools (web search via `httpx`, local extraction via `trafilatura`); the output is a typed `Verdict` (no free text) with a deterministic consistency pass + budget→finalize fallback. **Advisory, never classifying:** the verdict **never** automatically flips `risk_band`/`fix_lane` (web results are spoofable) — it shows, with citations, "candidate · verify", and the operator decides. Queue+request+cache live in one table `upstream_check_results` (key `(artifact_module, installed_version)`, TTL), which the research worker works through via the `status` column (`queued`→`running`→`done`/`error`) with `FOR UPDATE SKIP LOCKED`; it does **not** touch `llm_jobs`. **Air-gap:** omit the container (or turn the feature off) → zero outbound surface. Untrusted web/LLM output → marker neutralization in the prompt (like the chat), nh3 sanitization in the UI (no `|safe`). It does not call `llm_budget` (low-frequency, on demand; `request_limit` per run caps the cost). **Operator UI (Block AI-2, re-gated by AK/ADR-0064):** a "Check for upstream fix" button per group row in the `ESCALATE · No host patch — mitigate` card, **only** if the row has a researchable (has-fix lang-pkgs) finding; next to it a finding-level line "fixed upstream: `<component> <version>` — needs rebuild". The lookup runs asynchronously in the worker, the card polls via HTMX (`load delay`, only in the `running` state — it stops itself at `done`) and shows an advisory panel (idle/running/done/cached) with candidate release, `operator_action`, and source links ("candidate · verify"). The feature is configured in the LLM provider tab (enable toggle, search backend + Fernet secret, `llm_research_model`); a per-`(server,group)` guard protects the two routes (`POST`/`GET …/upstream-check`) against IDOR. Verdict fields + source URLs are rendered escaped (no `|safe`; non-`http(s)` schemes never as `href`).

**Provider abstraction.** `AsyncOpenAI` with `base_url`/`api_key`/`model` from the settings. **Exactly one preset ships — DeepInfra (default)** —, which pre-fills `base_url` plus both model fields; any other OpenAI-compatible provider (OpenAI, Together, Groq, Mistral, local Ollama/vLLM, LiteLLM proxy) is usable via **manual** `base_url`/model entry (not its own preset; only DeepInfra is tested). Only standard features (`messages`, `model`, `stream`, `temperature`, `max_tokens`) — no function calling, no Assistants API. The "Test connection" button probes **both** models individually (reviewer + chat, ADR-0057) with one mini request each and shows status, latency, model name, and token count per model.

**Risk reviewer (worker, two-pass).** The deterministic pre-triage (§12) supplies `pending` findings as input. **Pass 1 (group detection)** turns ungrouped findings into reusable `application_groups` with match patterns — input only finding identity, no server context. **Pass 2 (risk evaluation)** evaluates, since ADR-0053, **per fix lane** instead of per group: a mixed group produces up to **two separate LLM requests** (one each for the `patch` and the `mitigate` lane), with an identical host/exposure context block and the full selection budget per lane. Each call returns exactly one verdict — `risk_band` plus `worst_finding_id` and `reason` (max 256 chars); `pending`/`unknown` are forbidden as LLM output. The **`action_type` is no longer emitted by the LLM** but derived deterministically from `(fix_lane, risk_band)` and persisted (`patch+escalate/act → patch`, `patch+monitor → watch`, `patch+noise → none`, `mitigate+escalate → mitigate`, `mitigate+monitor → watch`, `mitigate+noise → none`). Band and lane are not orthogonal: **`act` is patch-only** (a non-host-applicably-fixable finding is either `escalate` or `monitor`/`noise`, never `act`) — band whitelist `patch: {escalate, act, monitor, noise}`, `mitigate: {escalate, monitor, noise}`, enforced in the lane prompt and the validator. The `mitigate` lane covers **everything not host-applicably fixable** — no fix **and** lang-pkgs/`other` fixes that only an upstream rebuild closes (ADR-0061 correctness: no false "Apply app update" recommendation). If an upstream fix exists, its version is shown finding-level (ADR-0064), not as its own lane. Pass 2 sets `risk_band_source='llm'`; pre-triage does not overwrite these findings on re-ingest.

The worker (`fathometer-llm-worker`) polls a job table with `SELECT … FOR UPDATE SKIP LOCKED` (concurrency-safe), respects `depends_on` (pass 2 waits for pass 1), and runs a stale reaper (in_progress > 10 min → requeue with backoff, from attempt 3 → failed). Two periodic re-enqueue sweeps keep the evals current, both via the **idempotent, fingerprint-gated + dedup-guarded** `enqueue_pass2_for_server`: the **backstop sweep** (5 min, TICKET-007) catches a failed post-pass-1 trigger; the **drift-reconciliation sweep** (15 min, TICKET-017) heals the "re-evaluation pending" drift hint (ADR-0052) itself — it covers the case where a group's OPEN set changes without new pass-1 activity (reopen/resolve/EPSS feed) and the lane eval drifts without a scan/triage enqueuing a re-eval. Liveness via a heartbeat column, no HTTP endpoint.

**Operational switches.** `BLOCK_P_LLM_MODE ∈ {off, observation, live}` (settings, default `off`); switching to `live` requires master-key confirmation and shows a **GDPR notice** (snapshot and findings context go to the external provider). In `observation` mode the worker writes `would_call` results instead of real calls, so the operator sees call frequency and token math before `live`. The **token budget** is the operator-controllable DB cap `Setting.llm_daily_token_cap` (provider tab "Daily token cap", reset 00:00 UTC; the initial value for fresh installs seeds from `FM_LLM_TOKEN_BUDGET_DAILY`, default 2 M) — it pauses the worker on exhaustion. Worker and web container read the same DB value (no env/pod drift, ADR-0014/ADR-0056). **Two-level caching:** the pass-1 cache is the `application_groups` library (deterministic pattern match Python-side: longest `path_prefix` → `pkg_name_exact` → `_glob` → `purl_pattern`); the pass-2 cache is `llm_risk_cache` with `cache_key = SHA256(group | fix_lane | findings_fp | cve_fp | server_context_fp)` (since ADR-0053 with a `fix_lane` salt, so the patch and mitigate lanes of the same group never hit the same entry; the `findings_fp` is built over the lane OPEN set — when a fix becomes available the finding migrates lanes, both lane fingerprints change → re-eval), TTL 30 days, LRU above 100 K. **Cache invalidation reacts to host/CVE state (ADR-0068):** `server_context_fp` includes the **running kernel** (`kernel_version`) and `cve_fp` includes `host_update_available`/`installed_version`/`fixed_version`, so a kernel upgrade or a host-update flip misses the cache. The same key is also the **enqueue gate** — `enqueue_pass2_for_server` persists the full `cache_key` on the `application_group_evaluations` row and skips a job only on an exact match (Gate 1), so a host/CVE change re-enqueues even when the lane OPEN-set is unchanged (legacy rows carry `cache_key = NULL` → one self-healing re-enqueue after deploy). Cross-server reuse: identical nodes share one cache entry (8 RKE2 nodes → one call). **Output validation** is strict: JSON schema, label regex, completeness check in pass 1, band whitelist and defensive pattern trim in pass 2 (`path_prefixes` must start with `/`, ASCII, bounds).

## 12. Triage signals and risk engine

The central UX problem is prioritization — a mid-size fleet easily produces several hundred open findings. Solved by display and sorting along the signals Trivy itself provides:

- **KEV (CISA Known Exploited Vulnerabilities)** — the sharpest signal: exploited *right now*, not just theoretically. A bold red badge, comes first in every sort.
- **EPSS** — probability of exploitation within 30 days (0–1), color-coded (green < 1%, yellow 1–10%, orange 10–50%, red > 50%).
- **CVSS-v3 base score** numeric (e.g. `8.7`) to differentiate within a severity tier, expandable to the vector.
- **Attack vector** (N/A/L/P) — a local flaw without local logins is less urgent than a network vector on an exposed service.
- **Fix availability** as a binary filter ("what can I update today").
- **CWE category** compactly, so experienced users can filter out classes.

**Risk band** is the primary sort key (deterministic mapping `RISK_BAND_SORT_RANK` in `app/services/risk_engine.py`): `escalate=70, act=60, mitigate=50, pending=40, unknown=30, monitor=20, noise=10, NULL=0`. Sort chain: **`risk_band` DESC → KEV DESC → EPSS DESC → CVSS severity rank DESC → `identifier_key` ASC** (the last key for a deterministic order). The UI filters on `?risk_band=<band>` resp. `?action_required=yes|no` (aggregates `escalate`/`act`/`mitigate`/`pending`/`unknown`).

**Pre-triage** (deterministic, no LLM, no host match) runs at ingest right after the snapshot persist. Inputs: max severity across all providers, EPSS, KEV flag, `snapshot_available`. First matching rule wins, defensively conservative:

1. no snapshot → **`unknown`** ("update agent to ≥ 0.3.0")
2. KEV-listed → **`pending`**
3. max severity ≥ HIGH → **`pending`**
4. EPSS ≥ 0.1 → **`pending`**
5. max severity == MEDIUM → **`monitor`**
6. otherwise (≤ LOW, EPSS < 0.1, not KEV) → **`noise`**

`pending` is the handoff to the LLM reviewer; `escalate`/`act`/`mitigate` is set exclusively by the LLM. Findings with `risk_band_source='llm'` are skipped by pre-triage. The thresholds live in code (re-tunable without a migration).

### Processing chain (end-to-end)

From scan arrival to risk band — as a navigation reference so the path need not be reconstructed from the code each time. Module/function names in parentheses.

1. **Receipt** (`app/api/scans.py`): gzip decompress (hard bound) → Pydantic parse of the envelope (`app/schemas/scan_envelope.py`, `Envelope`/`HostBlock`/`HostStateBlock`/`HostUpdateEntry`) → `202`, job into `scan_ingest_jobs` (idempotency via `payload_sha256`).
2. **Findings ingest** (`app/services/findings_ingest.py`, worker): one row built per vuln (`_build_finding_row`) — versions, severity, cause fields (`finding_class`, `target_path`, …). **Host-update join:** two maps from `host_updates` — lang-pkgs/`other` via `target_path` (`host_updates_map`), os-pkgs via `package_name` (`host_updates_by_pkg`, ADR-0066) → `host_update_available`/`owning_package`/`available_version`. Upsert on `(server_id, finding_type, identifier_key, package_name)`; no-longer-seen findings → `resolved`; redetected `resolved` → `open` (reopen-on-redetect, ADR-0052).
3. **Host-snapshot persist** (snapshot tables) + **pre-triage** (`risk_engine.pretriage`, §12): deterministic `{unknown, pending, monitor, noise}`. Only `pending` goes to the LLM.
4. **Group match / pass 1** (`app/workers/llm_worker.py`, `app/services/llm_risk_reviewer.py`): ungrouped findings → reusable `application_groups` (pattern match, pass-1 cache = the group library).
5. **Fix-lane partition** (`risk_engine.fix_lane_for` + SQL mirror `fix_lane_sql_case`; call site `pass2_input_selection.partition_by_lane`): each `(group, server)` is partitioned into `patch`/`mitigate`. **Truth table:** `not has_fix → mitigate`; `os-pkgs ∧ has_fix → patch` (**without** checking `host_update_available` — short-circuit!); `lang-pkgs/other ∧ has_fix ∧ host_update_available=true → patch`; otherwise `mitigate`.
6. **Pass 2 / risk evaluation** (`_render_pass2_prompt` + `_render_host_context`, §11): one LLM call **per lane**. The prompt contains host/exposure context (incl. `kernel (running):`, ADR-0066/0068) + per finding `sev/cvss/epss/kev/fixed=/vulnerable=/host_update=/path/av/…` (the per-finding labels are `vulnerable=` for the flagged on-disk artifact and `fixed=` for the resolving version, renamed from `installed=`/`fix=` in ADR-0068 to stop the "installed ⇒ active" misread; for kernel findings the comparator is the single-source `kernel (running):`, not `vulnerable=`). Output: `risk_band` + `worst_finding_id` + `reason`; `action_type` deterministic from `(lane, band)`. The pass-2 cache `llm_risk_cache` is keyed incl. `fix_lane` salt + lane-OPEN-set fingerprint; invalidation via `PASS2_PROMPT_VERSION` among others, and — since ADR-0068 — reacts to the **running kernel** and to `host_update_available`/`installed_version`/`fixed_version` (see §11).
7. **Persist & inheritance** (`application_group_evaluations`, `finding_group_inheritance`): one eval row per `(group, server, fix_lane)`; findings inherit the band from the row responsible for their server **and their lane**. `ACTION_REQUIRED_MAP` derives `action_required` from the band (not its own field).

### Known edge cases: Trivy multi-artifact & stale-fix false positives

Findings from the k3s kernel analysis (2026-06-14) — recorded because they are not obvious without reading the code:

- **Trivy scans ALL installed artifacts, not just the active ones.** The kernel is `installonly` (multiple versions coexist, `installonly_limit`). An old, **non-booted** kernel on disk is reported with its CVEs — with `installed=<old>`, `fixed=<newer>` — even though the **running** kernel long since over-satisfies the fix. That is correct Trivy behavior; Fathometer must classify it.
- **Stale-fix false positive:** such a leftover lands (os-pkgs ∧ `has_fix`) deterministically in `patch` → pass 2 sees "patch available + network AV + exposed" → `ACT`. The operator runs `dnf update` → "Nothing to do". A classic FP.
- **os-pkgs lane short-circuit:** `fix_lane_for` returns `patch` **immediately** for `os-pkgs ∧ has_fix`, **without** consulting `host_update_available` (the flag is a lane input only for lang-pkgs). For os-pkgs the flag is pure reviewer enrichment (ADR-0066), **not** a lane input — the lane stays invariant `patch` (Python `fix_lane_for` + SQL mirror `fix_lane_sql_case`).
- **os-pkgs `check-update` is no longer discarded (ADR-0066):** `collect_host_updates` now passes the result of the **one** `dnf check-update` run through for lang-pkgs **and** os-pkgs (os-pkgs join via `PkgName`, no `rpm -qf`). The dnf truth "there is no update for the kernel" thus lands as `host_update=none` on the finding.
- **Correction path implemented (ADR-0066 / Block AL, v0.27):** pass 2 corrects the FP itself (`act → noise`) when `fixed_version` is satisfied by the running/installed kernel. `Server.kernel_version` (= `uname -r`) as `kernel (running):`, the per-finding `installed_version` as `installed=`, and the os-pkgs anchor as `host_update=` are now in the prompt; a system-prompt STALE-ARTIFACT correction path guides the decision. **Lane unchanged**, no auto band flip in code, no outbound. Semantically correct in both directions: `running ≥ fixed` ⇒ FP ⇒ `noise`; `running < fixed` (fix installed but not booted) ⇒ stays actionable (reboot).

## 13. Audit log

Every state-changing action lands in `audit_events` with an actor (admin username / server name / `system`). Logged actions include: `finding.acknowledged|acknowledged.bulk|reopened|resolved|note.added|note.deleted`, `tag.created|renamed|color_changed|deleted`, `server.registered|revoked|retired|deleted|findings_deleted|group_changed|scan_interval_changed|tag.added|tag.removed`, `key.rotated.master|server`, `llm.provider_changed|mode_changed|budget_exhausted` (plus worker events `llm.job_picked|job_done|job_failed|job_reaped|jobs_queued|cache_hit`), `risk.pretriage_evaluated`, `settings.updated`, `auth.login|logout|failed`, `ratelimit.tripped`, `scan.queued|ingested|ingest_failed`. Bulk operations keep the affected IDs in `metadata`. In the async path a scan emits `scan.queued` (edge) → worker events → `scan.ingested` or `scan.ingest_failed`; idempotent re-inserts emit no second `queued`. The `/audit` view is paginated (50/page), filtered by date/actor/action/server, with CSV export of the live filtering.

## 14. Stale detection

Both computed live (`app/services/stale_detection.py`), nothing persisted. **Stale server:** `now() - last_scan_at > server.expected_scan_interval_h` (per server, default **24 h**; `last_scan_at` NULL **and** not retired → also stale) → yellow pill. **Stale Trivy DB:** `now() - trivy_db_updated_at > settings.stale_trivy_db_threshold_h` (default **30 h**) → orange pill with a note that findings may be incomplete. Both trigger only the visual signal (no notifications in the MVP) and are indirectly traceable in the audit via `scan.ingested` events.
